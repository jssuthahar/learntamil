# Learn Tamil — architecture

> Related: [DEVELOPMENT.md](DEVELOPMENT.md) (setup, testing, debugging) · [CONTENT.md](CONTENT.md) (data files) · [FEATURES.md](FEATURES.md) (every feature) · [SEO.md](SEO.md) · [../CLAUDE.md](../CLAUDE.md) (rules for Claude Code)

How the app is put together, why, and the rules to follow when you change it. Read this before you add a script, a stylesheet, a page or a game.

## 1. Principles

1. **No bundler, no server.** The browser runs the files exactly as they are in the repo. GitHub Pages serves the repo root. Anyone can open `index.html` and read the code. Node is only used for the tools in `tools/`.
2. **Public URLs never change.** Pages (`tamil-alphabet.html` …), `sw.js`, `manifest.webmanifest`, the images in `assets/` and the PDFs in `printables/` are linked from search results, social cards and installed apps. Moving them breaks those links.
3. **Generated, not hand-copied.** Anything that would otherwise be repeated is generated by `npm run build`: guide pages, script and style tags, the service worker's file list, the sitemap and the chat knowledge base.
4. **Children's privacy first.** Progress is stored only in the browser. Nothing a child types or says leaves the device. Analytics loads only after a grown-up taps **Allow**.
5. **Text is data.** All Tamil content and every child-facing message lives in `assets/js/data/` (see 2a), so it can be edited and reviewed in one place.

## 2. Layout

```text
assets/
  css/        00-tokens … 90-kids — numbered in cascade order
  js/
    core/       building blocks every feature uses
    data/       content (also read by the build tools)
    features/   one folder per area of the app
    services/   things shared by every page (install, analytics, support card, chat)
    app.js      the app shell: global controls + router — always last
  audio/      recorded letter sounds + manifest.js
tools/
  lib/assets.mjs    the one ordered list of styles and scripts
  lib/load-data.mjs runs assets/js/data/*.js in Node for the tools
  build-pages.mjs   generates pages, tags, sw.js lists, sitemap, llms.txt, chat data
  smoke-test.mjs    headless-Chrome test of every section and game
```

| Folder | Contains | May depend on |
| --- | --- | --- |
| `data/` | constants only (content and text), no DOM, no logic | other `data/` files |
| `core/` | `profiles` (storage), `dom` ($, effects), `letter-model`, `speech`, `sound`, `analytics` | `data/` |
| `features/x/` | one area of the app | `core/`, `data/`, `features/rewards/`; other features only through events or at run time |
| `services/` | install, analytics, support card, chat | `core/` |
| `app.js` | router | everything |

## 2a. Where text lives

**All Tamil content and every word the app says or shows to a child live in `assets/js/data/`.** To change wording, edit only these files. A Tamil teacher can review this one folder.

| File | What to edit there |
| --- | --- |
| `alphabet.js` | the 247 letters, sounds, hints, example words, letter labels (உயிர் எழுத்து, குறில் …), ஃ, sound-alike groups |
| `words.js` | picture words (`WORDS`) and word topics (`TOPICS`: numbers, colours … months) |
| `stories.js` | read-aloud stories |
| `rhymes.js` | Aathichoodi and sing-along rhymes |
| `festivals.js` | festival stories and words |
| `rewards.js` | badge names, Kili's levels, certificate level names |
| `pictures.js` | colouring pictures and colour swatches |
| `messages.js` | `TEXT`: praise, "try again", greetings, button labels, game titles, sticker / break / certificate wording |
| `faq.js` | **generated** from `tools/build-pages.mjs`, do not edit |

Rules:
- Code refers to text by name (`TEXT.tryAgain[0]`, `BADGES`, `STAGES`) and never writes Tamil inline. Pairs are `[Tamil, English]`.
- Placeholders such as `{name}` are filled with `fmt(TEXT.greetName, { name })` (in `core/dom.js`).
- Data files hold names only, never logic. When a badge is earned is decided by `BADGE_RULES` (`features/rewards/progress.js`); which questions a certificate level asks is set by `LEVEL_QUESTIONS` (`features/certificate/certificate.js`). Their `id` / `n` must match the data.
- Not in `data/`, on purpose: the page markup in `index.html` (search engines must read it without JavaScript), the certificate **question templates** (a sentence and the logic that fills it belong together), and grown-up screens (Parent dashboard, Ask Kili chat, the support note).
- `npm test` fails if a text name is wrong (it looks for `undefined` or an unfilled `{placeholder}` on the page).

## 3. How scripts share code

The scripts are classic `<script>` files, not ES modules. Top-level `const`, `let` and `function` names are shared by all of them, in the order they load.

**The rule:** while a file is loading, it may only use names defined by files **earlier** in `tools/lib/assets.mjs`. Inside event handlers and functions that run later (on a click, or on `DOMContentLoaded`), it may use any name. The router (`app.js`) loads last and opens the first section on `DOMContentLoaded`, after every file has run.

Break the rule and you get `ReferenceError: Cannot access 'x' before initialization`. `npm test` catches it.

Keep names that are shared across files few and obvious: `$`, `$$`, `speak`, `sayItem`, `Rewards`, `Progress`, `Profiles`, `showGame`. Anything a file uses only internally should stay inside an IIFE or an object (`TR`, `COL`, `LT`, `SayBack`).

### Events, for features that should not know about each other

| Event | Fired by | Meaning |
| --- | --- | --- |
| `lt:section` (`detail`: section id) | router | a section was opened: start it, or stop sound and timers |
| `lt:game` (`detail`: game id) | games hub | a game was picked: games in their own files start themselves |
| `lt:open` (`detail`: `stickers` / `parents`) | buttons anywhere | open a family dialog |

## 4. Routing

Each section is a URL hash: `#/uyir`, `#/mei`, `#/aytham`, `#/uyirmei`, `#/reading`, `#/stories`, `#/practice`, `#/certificate`, `#/little`. The router shows the matching `<section class="panel">` and fires `lt:section`. To add a section, add its panel to `index.html` and its id to `SECTIONS` in `app.js`.

## 5. Storage (localStorage)

All keys start with `lt-`. Read and write them in a `try`/`catch`, because private browsing can block storage.

| Kind | Keys | How to access |
| --- | --- | --- |
| **Per child** | `lt-progress`, `lt-best-<game>`, `lt-cert-name`, `lt-cert-seen`, `lt-spin-seen` | `Profiles.get(k)` / `Profiles.set(k, v)`. The first child uses the plain key; other children use `key@<id>`. |
| **Per device** | `lt-profiles`, `lt-profile`, `lt-theme`, `lt-sfx`, `lt-break`, `lt-consent`, `lt-push`, `lt-support`, install and notice flags | `localStorage` directly |

New progress fields go into `DEFAULT()` in `features/rewards/progress.js`. Old saves are merged over the defaults, so existing children keep their progress.

## 6. Build pipeline

```
assets/js/data/*.js ──► tools/lib/load-data.mjs ──► build-pages.mjs ──► guide pages, privacy, terms, 404,
                                                                          sitemap.xml, llms.txt, data/faq.js
tools/lib/assets.mjs ──────────────────────────────► build-pages.mjs ──► <link>/<script> tags in index.html
                                                                          and guide pages, sw.js PRECACHE
assets/css/NN-*.css ──► build-pages.mjs ──► assets/css/app.css (the one stylesheet pages load)
assets/js/data/*.js ──► build-pages.mjs ──► llms.txt (facts + links), llms-full.txt (all content as text)
all precached files ──► content hash ──────────────────────────────────► sw.js VERSION
```

`index.html` is hand-written, apart from the blocks between `<!-- NAME:START -->` and `<!-- NAME:END -->` markers (`STYLES`, `SCRIPTS`, `FAQ`, `FOOTER`, `SUPPORT`, `GUIDES`). Don't edit inside those blocks by hand.

## 7. Offline (service worker)

`sw.js` precaches every page and asset. `VERSION` is a hash of their contents, so any change produces a new version, and installed apps show *"A new version is ready · Refresh"*. Letter audio is cached separately (`lt-audio`) and is kept across versions.

## 8. Recipes

**Add a game**
1. Add a `.gcard` button with `data-game="mygame"` and a `<div class="game glass" id="g-mygame" hidden>` panel to `index.html`.
2. Create `assets/js/features/games/my-game.js`. Start it with `document.addEventListener('lt:game', e => { if (e.detail === 'mygame') start(); })`, and reward the child with `Rewards.win(el)` / `Rewards.miss()`.
3. Add it to `APP_SCRIPTS` in `tools/lib/assets.mjs`, after `features/games/hub`.
4. Put its styles in `assets/css/90-kids.css`, or in a new numbered file added to `STYLES`.
5. `npm run check`, then add the game to the smoke test's list.

**Add words or a topic:** edit `assets/js/data/words.js` (`TOPICS`). Reading, the games, spelling and the sticker book pick it up automatically. Get the Tamil reviewed.

**Add a guide page:** add it to `GUIDES` in `tools/build-pages.mjs`, then `npm run build`.

**Add a stylesheet or script:** add it to `tools/lib/assets.mjs` only, then `npm run build`. Never add a tag to the HTML by hand.

## 9. Testing

`npm test` serves the site, opens it in headless Chrome and fails on any JavaScript error. It checks that every asset exists, opens every section, starts every game, opens the rhyme, festival and family dialogs, runs a tracing check and loads the static pages. Run `npm run check` (build + test) before every push.

## 10. Decisions

| Decision | Why | Revisit when |
| --- | --- | --- |
| Classic scripts with shared globals, no bundler | Zero tooling to deploy; works from any static host; easy for contributors | The code grows past what one ordered list can manage. Then move to native ES modules (`<script type="module">`, still no bundler) one folder at a time, starting with `data/` and `core/`. |
| Site served from the repo root | Keeps GitHub Pages settings and every public URL unchanged | Tools and docs must not be public: move the site into `public/` and deploy it with GitHub Actions |
| Numbered CSS source files, joined into `app.css` at build | One render-blocking request for a fast first paint; the source stays small, ordered files | — |
| Images stay in `assets/` root | Their URLs are in social cards, the manifest and installed apps | — |
| Progress only in `localStorage` | No accounts and no personal data for children | Families ask for sync between devices |
